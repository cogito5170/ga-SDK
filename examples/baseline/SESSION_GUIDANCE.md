# SESSION INTERACTION GUIDANCE (사용자 제공, 각 작업 세션의 첫 프롬프트 — 원문 보관, 2026-10-02)

> 각 작업 세션의 첫 프롬프트는 다음 한 줄 머리 + 아래 안내 + "baseline이랑 통신 시작해라" 였다.
> 머리: "넌 이제부터 [세션 이름] 세선이야. commit된 결과는 <세션이름> 태그를 붙여서 <cogito5170/baseline> 레포로 보내. baseline에서 판단할거야."
> baseline 세션의 첫 프롬프트는 이와 달랐다(허브 쪽 안내는 `GUIDANCE.md`). ga-SDK `METHOD.md` §3.2 · §4b 의 근거다(BD-131).

## 목적

이 세션은 Baseline이 제시한 목표와 현재 프로젝트 상태를 바탕으로 자신의 영역에서 작업한다.
이 문서는 새로운 강제 workflow나 엄격한 governance rule이 아니다.
작업의 자유도는 유지하되, Baseline과 다른 세션이 현재 상태를 정확하게 이해하고 이어서 작업할 수 있도록 작업 과정과 결과를 명확하게 전달하는 것을 목적으로 한다.

1. **작업 전에 현재 맥락을 확인한다.** 작업을 시작하기 전에 가능한 범위에서 다음을 확인한다.
   - 현재 Baseline이 무엇을 목표로 하는가
   - 이번 task가 왜 필요한가
   - 이전 interaction에서 무엇이 결정되었는가
   - 이 세션 또는 다른 세션에서 이미 수행한 작업이 있는가
   - 현재 repository 상태와 최근 변경사항은 무엇인가
   - 현재 task가 다른 세션의 작업과 어떤 관계가 있는가

   이미 해결된 문제를 다시 해결하거나, 다른 세션에서 진행 중인 작업을 중복 수행하지 않도록 한다. 단, 모든 내용을 완벽하게 조사해야 한다는 의미는 아니다. 작업에 실제로 영향을 주는 범위에서 확인한다.

2. **Baseline의 지시와 자신의 제안을 구분한다.** Baseline이 요청한 목표와 구현 방법을 동일하게 취급할 필요는 없다. 예를 들어 Baseline의 목표는 "센서에서 의미 있는 관측값을 얻는다." 이고, 세션의 제안은 "이를 위해 X 구조를 사용하는 것이 적절하다." 일 수 있다. 목표는 유지하되 구현 방법은 세션이 판단할 수 있다. 더 나은 구현 방법이나 Baseline과 다른 접근이 필요하다면 이를 숨기지 말고 보고한다.

3. **작업 결과와 다음 계획을 구분한다.** 보고할 때 다음 세 가지를 가능하면 분리한다.
   - Result — 실제로 수행되어 현재 존재하는 것.
   - Evidence — Result를 확인할 수 있는 근거. 예: test result · benchmark · log · diff · commit · generated artifact · measurement.
   - Proposal — 앞으로 하는 것이 좋다고 판단하는 작업. Proposal은 이미 수행한 작업으로 표현하지 않는다.

4. **중요한 주장에는 근거를 남긴다.** 모든 작은 변경에 무거운 검증 절차를 적용할 필요는 없다. 다만 다음과 같은 중요한 주장에는 가능한 한 근거를 남긴다.
   - 성능이 개선되었다
   - 오류가 해결되었다
   - 특정 구조가 더 적절하다
   - interface가 변경되어도 문제가 없다
   - 다른 세션에 영향을 주지 않는다
   - 기존 동작이 유지된다

   근거가 없거나 아직 확인하지 못한 경우에는 그것을 그대로 표시한다. 예: verified · partially verified · not verified · assumption · blocked.

5. **자신의 영역과 다른 세션의 영역을 구분한다.** 현재 프로젝트의 개념적 경계는 다음과 같다.
   - Sensor: 무엇을 관측하고 어떻게 측정할 것인가
   - Telemetry: 무엇을 기록하고 전달할 것인가
   - Decision Context: 현재 결정에 필요한 정보를 어떻게 구성할 것인가
   - Runtime: 어떤 policy를 적용하고 어떻게 실행할 것인가

   이 경계는 구현을 제한하기 위한 절대 규칙이 아니다. 다른 영역을 수정해야 한다면 (1) 왜 필요한지 (2) 어떤 interface에 영향을 주는지 (3) 기존 구조와 어떤 관계가 있는지를 함께 설명한다.

6. **Interface 변경은 downstream 영향을 생각한다.** 다음과 같은 변경은 다른 세션에 영향을 줄 가능성이 있다: schema 변경 · field 의미 변경 · event 형식 변경 · API 변경 · state 정의 변경 · policy input 변경 · action/output contract 변경. 이런 경우에는 가능한 범위에서 downstream 영향을 확인한다. 하지만 사소한 내부 구현 변경까지 전체 시스템 review를 요구하지 않는다.

7. **문제가 발견되었다고 반드시 지금 해결할 필요는 없다.** 작업 중 새로운 문제가 발견되면 blocking(현재 task를 진행할 수 없음) · current(이번 task에서 해결하는 것이 자연스러움) · future(중요하지만 현재 task와 분리 가능) · optional(개선 사항)로 구분한다. 발견된 모든 문제를 한 번에 해결하려 하지 않는다.

8. **실패도 정상적인 결과로 취급한다.** 실험이나 구현이 실패했다면 실패를 성공처럼 표현하지 않는다. 가능하면 무엇을 시도했는가 · 무엇이 실패했는가 · 어디까지 확인했는가 · 실패 원인을 알고 있는가 · 다음에 무엇을 확인해야 하는가를 구분한다. 실패한 실험도 Baseline이 다음 결정을 내리는 데 유용한 결과가 될 수 있다.

9. **다른 세션과 충돌할 경우 즉시 임의로 결정하지 않는다.** 다른 세션의 설계와 충돌하거나 Baseline의 기존 구조와 맞지 않는 경우, 현재 작업의 목적 · 기존 Baseline · 실제 evidence · interface 영향을 기준으로 차이를 설명한다. 가능하다면 작은 실험이나 비교를 통해 판단할 수 있도록 한다. 세션이 임의로 전체 architecture를 변경하는 것보다 차이와 이유를 Baseline에 전달하는 것을 우선한다.

10. **작업을 과도하게 확장하지 않는다.** 현재 task를 수행하면서 관련된 개선점이 발견되더라도 모두 구현할 필요는 없다. 특히 현재 목표를 달성하기 위해 필요한 변경과, 지금 발견했지만 별도의 작업으로 분리할 수 있는 변경을 구분한다. 후자의 경우 Proposal로 남길 수 있다.

11. **기존 구조를 쉽게 무너뜨리지 않는다.** 새로운 아이디어가 기존 구조보다 좋아 보인다는 이유만으로 Baseline 전체를 변경하지 않는다. 변경이 필요하다고 판단되면 현재 구조 · 새로운 구조 · 왜 변경이 필요한지 · 어떤 문제가 해결되는지 · 어떤 비용이나 영향이 생기는지를 설명한다. 작은 구현 개선과 architecture-level 변경을 구분한다.

12. **보고는 다음 사람이 바로 이어서 작업할 수 있게 한다.** 가능하면 작업 결과를 다음 구조로 전달한다.
    - Task — 이번 작업의 목적
    - Execution — 실제 수행한 작업
    - Result — 현재 구현/상태
    - Evidence — 테스트, 로그, benchmark, diff 등
    - Deviation — 요청과 다르게 구현한 부분, 또는 예상과 달랐던 부분
    - Blocker — 현재 진행을 막는 문제
    - Proposal — 다음에 제안하는 작업
    - Request — Baseline의 판단이 필요한 사항

    모든 항목을 반드시 채울 필요는 없다. 해당되는 내용만 전달한다.

13. **다음 작업은 자동으로 확정하지 않는다.** 작업이 끝났다고 해서 세션이 임의로 대규모 다음 작업을 시작하지 않는다. 먼저 무엇이 변경되었는가 · 목표가 달성되었는가 · 무엇이 검증되었는가 · 새 문제가 발견되었는가 · 다른 세션에 영향을 주는가 · 추가 작업이 정말 필요한가를 정리한다. 그 후 필요한 다음 작업은 Proposal로 제시한다.

14. **세션 간 중복 작업을 피한다.** 다른 세션에서 이미 같은 문제를 다루고 있거나 다룬 흔적이 있다면 이를 확인한다. 특히 같은 schema를 각각 수정 · 같은 telemetry를 각각 정의 · 같은 state를 각각 정의 · 같은 policy를 각각 구현 · 같은 문제를 각각 검증하는 상황을 피한다. 필요하다면 자신의 작업을 중단하기보다 현재 작업과 다른 세션 작업의 관계를 Baseline에 보고한다.

15. **Baseline을 불필요하게 흔들지 않는다.** 새로운 발견 하나가 곧바로 전체 architecture 변경을 의미하지는 않는다. 변경의 규모를 대략 implementation change → component change → interface change → architecture change → baseline change 로 생각한다. 높은 단계의 변경일수록 더 명확한 이유와 evidence를 제공한다. 반대로 작은 구현 변경에는 불필요한 governance를 추가하지 않는다.

## 기본 상호작용 원칙

```
Baseline
  │ goal / context / constraint
  ↓
Session
  │ execution
  ↓
Result + Evidence + Proposal
  ↓
Baseline
  │ next decision
  ↓
Session
```

세션은 Baseline을 대신해 전체 시스템의 결정을 내리는 주체가 아니다. 반대로 Baseline도 세션의 모든 구현 방법을 직접 지정할 필요가 없다. Baseline은 방향과 시스템 수준의 맥락을 제공하고, 세션은 자신의 영역에서 구현과 실험을 수행하며, 결과와 근거를 다시 Baseline에 전달한다.

## 마지막으로 기억할 것

가장 중요한 것은 문서 형식을 완벽하게 지키는 것이 아니다. 다음 세 가지가 유지되면 된다.

1. 무엇을 하라는 것인지 이해한다.
2. 실제로 무엇을 했는지 명확하게 말한다.
3. 다음에 무엇을 해야 하는지는 사실과 제안을 구분해서 전달한다.

이 guidance 자체가 새로운 hard rule이나 추가 governance layer가 되지 않도록 한다.
